Yes, it will **probably make a meaningful difference**, even if the camera sensor/HAL is still producing 720p/15fps.

The reason is that thermal load is not only the camera. For long streaming on glasses, the big contributors are usually:

```text
camera sensor + ISP
+ frame copies / color conversion
+ video encoder
+ packetization / encryption
+ Wi-Fi or cellular radio
+ CPU wakeups / app logic
```

Dropping to **5fps before encoding and network send** leaves the camera/ISP cost mostly unchanged, but can reduce encoder work, bitrate, packet rate, radio airtime, CPU wakeups, and backend traffic.

## Practical answer

| Pipeline                                                                                 |                    Expected thermal benefit |
| ---------------------------------------------------------------------------------------- | ------------------------------------------: |
| Capture 15fps, encode 15fps, stream 15fps                                                |                                    Baseline |
| Capture 15fps, drop to 5fps **before encoder**, encode/stream 5fps                       |                          Usually noticeable |
| Capture 15fps, encode 15fps, then drop packets/frames later                              |                Almost no benefit on glasses |
| Capture 15fps, app receives all frames and does conversion/CV on all 15, then drops to 5 |                    Partial or small benefit |
| Camera HAL truly supports 5fps capture                                                   | Best, but sounds unavailable on your device |

So the important thing is **where you drop frames**.

## Why 5fps can help even though the camera is still 15fps

Android Camera2's `CONTROL_AE_TARGET_FPS_RANGE` controls the camera/AE capture frame-rate range, but the actual achievable frame rate depends on stream configuration and device support. If the device only exposes 15fps as the minimum useful capture mode, the camera subsystem may still run at 15fps. ([Android Developers][1])

However, the encoder side is separate. Android's `MediaFormat.KEY_FRAME_RATE` is used as the intended encoder frame rate and rate-control hint, and Android also has `KEY_MAX_FPS_TO_ENCODER`, which can tell a surface-input video encoder to drop excessive frames before feeding the encoder. ([Android Developers][2])

That means:

```text
720p15 camera input
-> only 5fps reaches encoder
-> lower bitrate
-> fewer packets
-> less radio/network work
-> less heat
```

## My recommendation

For long-running smart-glasses streaming, I would design the app as:

```text
Default: 720p / 5fps stream
Burst mode: 720p / 15fps only when needed
Thermal fallback: 3fps, lower bitrate, or pause video
```

Implementation-wise:

1. **First try to request lower capture FPS**, even if you expect it to fail:

   ```kotlin
   CaptureRequest.CONTROL_AE_TARGET_FPS_RANGE = Range(5, 5)
   ```

   If unsupported, fall back to `Range(15, 15)`.

2. **Drop frames before encoding**, not after encoding.

3. If using `MediaCodec` surface input, consider:

   ```kotlin
   format.setInteger(MediaFormat.KEY_FRAME_RATE, 5)
   format.setFloat(MediaFormat.KEY_MAX_FPS_TO_ENCODER, 5.0f)
   ```

   `KEY_MAX_FPS_TO_ENCODER` is specifically meant to limit how many source frames are fed into the encoder in surface-input mode. ([Android Developers][2])

4. **Lower bitrate with FPS**. Do not keep the same bitrate as 15fps unless you intentionally want much higher per-frame quality. For example:

   ```text
   720p15: maybe 800-1500 kbps, depending on quality/content
   720p5:  maybe 250-600 kbps
   ```

   Actual numbers need device and scene testing.

5. **Adjust keyframe interval**. At 5fps, avoid accidentally making keyframes too frequent. For long streaming, something like 2-5 seconds per keyframe is often more reasonable than keyframe every few frames, unless latency/recovery requirements demand otherwise.

## Thermal control

Use Android's thermal APIs as a feedback loop, not only a static setting. Android exposes thermal headroom/status, and its own guidance says apps should reduce workload when thermal pressure rises, including reducing frame rate, lowering fidelity, or reducing network connectivity work. ([Android Developers][3])

A simple policy:

```text
Normal:     720p / 5fps
Thermal light: reduce bitrate
Thermal moderate: 3fps or lower resolution if possible
Thermal severe: pause video or send still frames
```

One caveat: Android notes that some devices do not fully support thermal APIs, and `getThermalHeadroom()` should not be called more than once every 10 seconds. ([Android Developers][3])

## Bottom line

**It is not "basically the same."**
Even if camera capture remains 720p/15fps, streaming **5fps before encoding/network** should usually reduce heat, battery drain, and network bandwidth. It will not reduce the camera/ISP portion, so the gain may be modest on some glasses, but on a constrained glasses form factor it is very likely worth doing.

The best validation is an A/B test on the actual glasses:

```text
A: 720p15 encode + stream 15fps
B: 720p15 capture, encode + stream 5fps
C: 720p15 encode, then drop after encode
```

If B runs cooler than A and C looks close to A, you have confirmed that encoder/network work is a meaningful thermal source on that hardware.
