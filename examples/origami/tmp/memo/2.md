Yes, it is feasible.

## Android side

Use **MediaProjection API**. Android has supported screen capture via `android.media.projection` since Android 5.0 / API 21, and it captures the display or app window into a `Surface`. Your app can then record, cast, or process that stream in real time. ([Android Developers][1])

Typical pipeline:

```text
User consent dialog
  -> MediaProjection token
  -> VirtualDisplay
  -> Surface
  -> MediaCodec H.264/AV1/VP8 encoder
  -> transport to backend
```

For streaming, avoid screenshot-by-screenshot capture. Instead, pipe the `VirtualDisplay` directly into an encoder `Surface` from `MediaCodec.createInputSurface()`. Android's `MediaCodec` supports using an input `Surface` for video encoders, which avoids copying frames through CPU memory. ([Android Developers][2])

## Important Android constraints

1. **You need explicit user consent every session.**
   Android requires user approval before a `MediaProjection` session, and on Android 14+ the token is effectively one-time-use for one `createVirtualDisplay()` call. ([Android Developers][1])

2. **You need a foreground service for ongoing capture.**
   For apps targeting Android 14+, declare:

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PROJECTION" />

<service
    android:name=".ScreenStreamService"
    android:foregroundServiceType="mediaProjection"
    android:exported="false" />
```

Android requires the `mediaProjection` foreground service type and permission for this use case. ([Android Developers][1])

3. **Android 14+ lets users share either one app or the full screen.**
   If the user picks single-app sharing, system UI like status bar, navigation bar, and notifications are excluded. ([Android Developers][1])

4. **Some screens cannot be captured.**
   Apps that use `FLAG_SECURE`, like banking/password screens, can block screenshots and screen sharing output. ([Android Developers][3])

5. **The user can stop capture from the system UI.**
   Android shows active projection tokens in Quick Settings and users can revoke them, so your service must handle black frames or stopped streams. ([Android Developers][4])

## Backend transport options

For "live video to our backend", I would choose based on latency:

| Transport                                        | Best for                                                             | Notes                                                                                                                                     |
| ------------------------------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **WebRTC**                                       | Lowest latency, interactive viewing, remote support, live monitoring | Best default if you need sub-second latency. WebRTC supports real-time video/audio/data across browsers and native clients. ([WebRTC][5]) |
| **WHIP over WebRTC**                             | Clean backend ingest API                                             | WHIP is now an RFC for WebRTC ingestion into streaming services/CDNs. ([RFC Editor][6])                                                   |
| **RTMP/SRT**                                     | Broadcast-style ingest                                               | Easier if your existing infra already accepts RTMP/SRT, but latency is usually worse than WebRTC.                                         |
| **WebSocket/WebTransport with raw H.264 chunks** | Custom backend control                                               | Possible, but you must solve muxing, timestamps, packet loss, backpressure, reconnection, and playback yourself.                          |

## Recommended architecture

```text
Android app
  MediaProjection
  -> VirtualDisplay
  -> MediaCodec encoder, H.264 or VP8
  -> WebRTC publisher / WHIP client
  -> Your backend ingest
  -> SFU / recorder / viewer pipeline
```

For an MVP:

* **Android:** `MediaProjection + ForegroundService + MediaCodec`
* **Transport:** WebRTC, ideally WHIP if your backend can support it
* **Backend:** SFU or WHIP-compatible ingest server
* **Optional recording:** store incoming stream server-side as MP4/HLS after ingest

## Audio

If you also want audio:

* **Mic audio:** use `RECORD_AUDIO` plus the `microphone` foreground service type if running as foreground service. ([Android Developers][7])
* **Device/app playback audio:** use Android's `AudioPlaybackCapture API`, available from Android 10 / Q, but capture is permission-gated and apps can restrict whether their audio can be captured. ([Android Developers Blog][8])

## Bottom line

Yes, you can build it. The clean implementation is:

```text
MediaProjection -> MediaCodec -> WebRTC/WHIP -> backend
```

The main product constraints are user consent, foreground notification, Android 14 token/session rules, and secure screens being blacked out.
