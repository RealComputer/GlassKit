## Recommended architecture

Use **WebRTC ingest from Android to your backend**, with **two separate video tracks**:

* Track 1: `camera`
* Track 2: `screen`
* Optional: audio track, telemetry/control data channel

Prefer **one `RTCPeerConnection` with two video tracks** if your backend supports multi-track ingest. WebRTC's `addTrack()` is designed for adding media tracks to a peer connection, and WHIP is now an IETF standard for WebRTC ingestion into streaming services/backends. ([MDN Web Docs][1])

```text
Android app
  ├─ Camera capturer -> hardware encoder -> WebRTC video track: camera
  ├─ MediaProjection -> screen capturer -> hardware encoder -> WebRTC video track: screen
  ├─ optional mic -> WebRTC audio track
  └─ data channel / HTTPS -> stats, control, bitrate hints

Backend edge
  ├─ WHIP endpoint or custom WebRTC signaling
  ├─ ICE/STUN/TURN
  ├─ WebRTC media server / SFU / custom Pion service
  └─ fan out encoded RTP streams

Processing backend
  ├─ decode only where needed
  ├─ server-side composition / ML / OCR / storage
  ├─ frame sampling / downscaling
  └─ control loop back to device
```

## Why this is the best default

For a lightweight Android client, the app should do only:

1. capture,
2. hardware encode,
3. adaptive network send.

Push everything else to the backend. Avoid client-side compositing, CV, OCR, redaction, transcoding, thumbnails, or frame analysis unless absolutely necessary.

Android `MediaProjection` captures display or app-window content into a virtual display rendered to a `Surface`, and WebRTC's Android `ScreenCapturerAndroid` already uses `MediaProjection` with `SurfaceTexture`, which fits a low-copy capture path. ([Android Developers][2])

For encoding, stay on the `Surface` / hardware codec path. Android `MediaCodec` supports encoder input surfaces, which avoids feeding raw CPU buffers into the encoder. ([Android Developers][3])

## Android-side design

### Capture

Use:

* **Camera**: WebRTC `Camera2Capturer` / camera capturer path, not CameraX `VideoCapture` unless you are recording to file.
* **Screen**: `MediaProjection` + WebRTC `ScreenCapturerAndroid`.
* **Encoding**: WebRTC hardware encoder factory / `MediaCodec`.
* **Transport**: WebRTC over UDP with TURN fallback.

CameraX `VideoCapture` is oriented around recording video/audio, compressing, muxing, and writing to disk, so it is not the best primary abstraction for live low-latency backend ingest. ([Android Developers][4])

### Foreground service and permissions

You will need a visible foreground service. For Android 14+, foreground service types must be declared, and camera/media projection each have their own service type and permission requirements. ([Android Developers][5])

Typical manifest shape:

```xml
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_CAMERA" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PROJECTION" />

<!-- Add only if streaming mic audio too -->
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MICROPHONE" />

<service
    android:name=".StreamingService"
    android:exported="false"
    android:foregroundServiceType="camera|mediaProjection" />
```

Media projection requires explicit user consent for each session, and on Android 14+ the projection token is single-use for a single `createVirtualDisplay()` call. You also need to handle `onStop()`, resize, rotation, lock screen termination, and the system screen-sharing chip behavior. ([Android Developers][2])

## Backend choices

### Best MVP backend

Use one of these:

| Backend option                     | When to choose it                                                                                                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **LiveKit Ingress / WebRTC stack** | Fastest path if you want production-grade WebRTC infra. LiveKit Ingress supports WHIP, RTMP/RTMPS, files, and SRT. ([LiveKit Docs][6])                             |
| **mediasoup**                      | Good if you want a programmable SFU and already run Node.js/TypeScript infra. mediasoup is signaling-agnostic and supports WebRTC and plain RTP I/O. ([GitHub][7]) |
| **Pion WebRTC**                    | Good if your backend is Go and you want custom ingest, RTP routing, and processing control. Pion has WHIP/WHEP examples. ([Go Packages][8])                        |
| **GStreamer / FFmpeg workers**     | Good downstream of WebRTC ingest for decode, transcode, muxing, frame extraction, ML, and storage.                                                                 |

For your use case, I would start with:

```text
Android WebRTC client
  -> WHIP or custom WebRTC signaling
  -> WebRTC ingest service
  -> RTP/encoded-frame fanout
  -> processing workers
```

Use **custom WebSocket signaling** instead of WHIP if you need richer session control, such as dynamic track start/stop, custom auth, per-track metadata, backend-driven bitrate policy, or live processing commands. Use **WHIP** if you want a clean standard ingest interface and your server supports your required multi-track behavior.

## Track strategy

### Preferred

Use **two separate tracks**:

```text
PeerConnection
  ├─ video track: camera
  └─ video track: screen
```

Benefits:

* Backend receives camera and screen independently.
* Backend can process, store, sample, or compose each stream differently.
* You avoid client-side GPU composition.
* You can set different FPS/resolution/bitrate targets.

### Alternative

Use **client-side composition** into one video track only when bandwidth is more important than backend flexibility:

```text
screen + camera PiP -> one composed Surface -> one encoder -> one WebRTC track
```

This saves upload bandwidth and one encoder, but it costs client GPU work and loses separate camera/screen streams.

## Initial encoding defaults

Start conservative and adapt upward:

| Source      |             Resolution |       FPS |           Bitrate target |
| ----------- | ---------------------: | --------: | -----------------------: |
| Screen UI   |               720p max | 10-15 fps |     800 kbps to 2.5 Mbps |
| Camera      |           360p to 720p |    15 fps |     400 kbps to 1.5 Mbps |
| Both active | Prefer lower FPS first | 10-15 fps | Device/network dependent |

Use **H.264** as the default codec for broad Android hardware encoder support and backend compatibility. Add VP8/VP9/AV1 only after device testing, because power and hardware support vary significantly by device generation.

## Battery and thermal rules

The biggest battery costs will be:

1. two active capture sources,
2. two hardware video encoders,
3. cellular uplink,
4. screen-on time,
5. unnecessary preview/rendering.

Implementation rules:

* Do not convert frames to `Bitmap`.
* Do not use `ImageReader`/CPU YUV paths unless needed.
* Do not run ML/OCR on-device.
* Do not render local previews unless required.
* Start at 10-15 fps, not 30 fps.
* Prefer server-side downscaling, frame sampling, redaction, and composition.
* Pause or stop a track when backend does not need it, rather than sending black frames.
* Use WebRTC stats to dynamically lower resolution/FPS/bitrate under heat, packet loss, or low battery.

## When not to use WebRTC

Avoid WebRTC only if one of these is true:

| Condition                                                                        | Better option                        |
| -------------------------------------------------------------------------------- | ------------------------------------ |
| Latency of several seconds is acceptable and you only need one composed stream   | RTMP/RTMPS or SRT                    |
| You fully control network and devices and want a custom appliance-style pipeline | Raw `MediaCodec` + RTP/SRT/QUIC      |
| You only need low-frequency screenshots                                          | Periodic JPEG/WebP upload, not video |
| Backend only needs final picture-in-picture output                               | Client-side composition + one stream |

For your stated requirements, **WebRTC is the right default**.

## Concrete recommendation

Build this:

```text
Android:
  Kotlin foreground StreamingService
  WebRTC native Android
  Camera capturer -> track "camera"
  ScreenCapturerAndroid -> track "screen"
  Hardware H.264 encoding
  One PeerConnection if possible
  TURN fallback
  DataChannel for stats/control

Backend:
  WHIP-compatible WebRTC ingest or custom signaling
  LiveKit / mediasoup / Pion edge
  Per-track RTP routing
  Decode only in processing workers
  Server-side composition, ML, recording, frame sampling
  Control loop to change bitrate/FPS/resolution
```

The key design decision: **send camera and screen as separate hardware-encoded WebRTC tracks, and keep the Android app dumb.**
